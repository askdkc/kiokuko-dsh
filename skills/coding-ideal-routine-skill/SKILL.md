# Coding Ideal Routine

目的は、変更箇所のテストを通すだけでなく、ユーザーが普段行う操作で要求を満たすこと。既存の作業規約とユーザーの目的・環境・権限を守り、変更リスクに見合う最小限の検証で根拠を積み上げる。

## 1. 作業の種類と完了条件を決める

- 質問・調査・計画だけなら、その回答を完成させる。依頼のない編集やテスト追加、記憶の読み直しを始めない。
- 修正・機能追加なら、現状の実装、関連テスト、利用手順、実行可能な環境を確認する。コードを書く前に「誰が、どの入口から、何をして、何が観測できれば成功か」を短く定義する。
- 挙動を変えない文章修正やリファクタリングでは、変更に適した検証を選ぶ。Red が不要な理由を明記し、無意味な失敗を作らない。文章・設定でも利用手順や実行結果が変わるなら挙動変更として扱う。
- 不明点は既存の仕様と利用実態から解消する。結果や権限を左右する曖昧さだけ確認し、勝手な機能拡張をしない。

## 2. 部品ではなく、つながった利用経路を見る

変更に関連する通常の操作を、入口から観測可能な結果までたどる。該当する場合は、配布・インストール → 読み込まれる指示／設定 → 公開ツールや UI → 実処理 → ユーザーの成果物までを対象にする。

- 各部品の成功を、連結した経路の成功に置き換えない。生産側が実際に出す値を、消費側がそのまま受け取れるか確かめる。
- 例: インストールされた指示が出す alias と prefix を組み合わせた参照が、実際の読み取りツールで解決できること。alias 単独、prefix 単独のテストだけでは不足する。
- 配布物や導入処理が関係する変更では、隔離した環境へ正規の方法で導入した成果物を境界テストに使う。ソース直読みや内部関数の直接呼び出しだけで代替しない。
- 本番相当の入力は、公開された利用契約や実際の成果物から得る。テスト側で canonical 名へ書き換える、欠けた設定を注入する、製品の不具合を補正するなどの救済をしない。
- AI が操作する製品では、被試験 AI に修正箇所・正解・特別な操作順を教え込まない。通常配布される指示と自然な依頼で試す。評価側だけが正解を保持する。

## 3. 挙動変更は Red → Green

1. 要求・仕様から期待値を先に決め、最小の回帰テストまたは受け入れテストを書く。新機能は未実装時に要求を満たさないことを表す。
2. 修正前のコードで実行し、意図した挙動の不一致で失敗することを確認する。構文エラー、依存不足、認証失敗は Red の証拠に数えない。
3. 原因を直す最小限の変更を行い、同じテストが通ることを確認する。テストを削除・弱体化したり、実装の出力を正解にして通したりしない。
4. 必要な整理を行い、関連する既存テストと経路の受け入れ検証を再実行する。

修正前の状態を実行できないなど、正当な制約で Red を確認できない場合は、その理由と代替証拠を残す。可能なら隔離した旧版で再現する。Red を観測していないのに「再現済み」「TDD 完了」と報告しない。

## 4. 独立した正しさと、必要な範囲を検証する

- 期待値は要求・仕様・手計算・独立した fixture などから得る。被試験コードと同じ変換関数を使って期待値を計算しない。AI の「成功しました」やログの文字列だけを正解判定にしない。
- 影響する境界値、条件の組み合わせ、失敗後の復旧を選ぶ。個々の成功例だけでなく、今回壊れ得る接続部分を含める。
- 復旧が関係する変更では「一度失敗 → 許可された修正／再試行 → 正しい最終状態」を確認する。成功した最後の一回だけでなく、不要な副作用・重複・失敗状態の残留も確認する。
- 高速で決定的な回帰テストを基本にする。関連する公開境界のテストを加え、モックで確認できない実サービス固有の挙動がある場合だけ、目的と終了条件を決めて live 検証する。
- 毎回の全ホスト・全モデル・全 API の高額な総当たりは行わない。変更が触れる接続とリスクに応じて選び、未検証の範囲を残す。実サービスへの送信、費用、認証、外部変更は既存の許可範囲に従う。

## 5. 障害と権限を混同しない

- ツール引数・構文・依存関係・テスト環境の問題は、原因を特定し、許可された範囲で修復して再実行する。最初の失敗だけで作業を打ち切らない。
- 明示的なアクセス拒否・承認不足は別扱い。別ツール、別アカウント、別経路で迂回しない。必要な操作・対象・不足する許可を報告し、その操作を止める。
- 再試行は原因に対する変更と観測可能な進展がある場合に行う。同じ条件で無限に繰り返さない。解消不能な制約や追加判断が必要なら、独立して進められる作業を終え、ブロッカーを明示する。

## 6. 最終版の証拠で完了を判定する

- 最後の変更を含む revision／作業ツリーで検証する。ビルド・配布物が必要なら再生成し、それを使う。検証後に内容を変えた場合は影響する検証をやり直す。
- 実行した対象、検証数、終了状態、assertion、成果物を確認する。skip、空 suite、no-op、終了コード 0 だけ、古い成果物、自己申告を成功の代わりにしない。無関係な既存 skip がある場合も、必要な受け入れ条件まで通ったことを別に確かめる。
- 差分に無関係な変更やテスト専用の抜け道がないことを確認する。未検証の経路は「未検証」、環境障害は「検証不能」と区別し、全体成功に混ぜない。
- ユーザーには、変更内容、確認できた通常利用、実行した検証と結果、残る制約を簡潔に報告する。再現・実装・ローカル検証・公開／本番反映は別々の事実として扱う。許可のない公開やデプロイを完了条件に追加しない。

この Skill は実行時の判断を支援する手順であり、ホストによる毎回の呼び出しや不具合の完全防止を保証する仕組みではない。
